LOOM / THE FULL STORY

Loom｜陆兮个人 AI 工作助手

把日常交流中的工作意图，织成持续推进的成果。

DeepSeek Harness 团队在《Super-agent 设计探索：迈向更自主的 Agent 系统》中，提出了一种持续存在、能够响应环境事件并推进多项工作的 Agent 形态。它强调连续、高效、主动和持久：系统负责组织上下文与执行任务，用户将注意力集中到决策和验收上。这为 Loom 提供了重要的架构启发。

我们希望把这一思路带入更广泛的日常办公场景。Loom 由陆兮独立推进，在 DeepSeek 开源研究原型和 Harness 的基础上，探索如何让个人助手自然地进入真实工作流程。

工作需求，常常产生在交流中

一句“可以汇总一下这几轮的结果”，可能出现在飞书讨论中；一份报告的关键要求，可能分散在文件、后续补充和几次修改里。为了让 AI 完成工作，用户需要先找到相关资料，整理背景，打开会话，描述目标，再把讨论中的变化不断同步过去。任务完成后，还需要核对内容、整理文件，将结果送回原来的工作环境。

模型承担了越来越多的执行工作，但用户仍然承担着大量组织工作：决定什么时候调用 AI、给它哪些上下文、记住每个会话在做什么、检查任务有没有偏离，以及把结果重新接回业务流程。

随着同时推进的任务增多，这些组织和跟进成本会不断增加。我们认为，个人 AI 助手值得解决的一个核心问题，就是让用户用更少的注意力，持续获得可用的工作成果。

因此，脱离以 Session 为中心的交互方式值得探索。用户可以围绕目标、任务和成果组织工作；底层会话则由系统按需创建和管理。一个任务可以从飞书中的讨论开始，在后台执行，在桌面端接受检查，再回到原线程交付。用户补充要求时，也应当能够沿着同一个任务继续。

这种方式也需要逐步建立信任。用户需要知道助手关注了什么、依据什么开工、目前进行到哪一步，以及什么时候可以介入。Loom 的产品设计，将后台自主推进与清晰的控制入口放在同等重要的位置。

共同形成的工作上下文，是值得积累的资产

我们往往不愿意舍弃一段对话了很久的 Session，因为里面积累了大量背景、约束、偏好和反复校准后的理解。新开会话时重新讲述一遍，不仅费力，也可能漏掉真正影响判断的细节。用户珍惜的，是这段交流中逐步建立起来的理解。

工作中的群聊同样如此。同事们围绕目标提出问题、补充条件、质疑方案、纠正误解，逐渐形成共识。这些对话包含任务结论，也包含结论的适用条件、取舍理由、尚未解决的问题和后来发生的变更。它们是人们共同建设工作环境的过程，也是 Agent 执行工作所需的重要依据。

当我们自己总结群聊和文档，再转述给 Codex 等执行工具时，这些语义容易在压缩和转述中遗漏。例如，“重复回调只能处理一次”需要同时保留“失败后仍允许正常重试”这一条件；缺少后者，执行者可能得到表面正确却不适用于真实工作的方案。反复重建上下文带来的成本，也包含误解、返工和解释。

Loom 希望让共同办公环境中积累的上下文被保留、被理解，并在授权范围内被后续工作接续。长期方向是将原始讨论、相关文档版本、已确认决策、任务与产物关联起来，使新任务能够按需找到相关依据，而用户可以随时回到来源核对。底层会话可以更换，已经形成的工作理解应当有独立、可追溯的承载方式。

这也要求我们认真处理上下文的质量。保留下来的内容需要区分建议与决定、事实与推测、当前规则与过期方案；摘要应保留回到来源的入口，使用时检查资料是否仍适用、当前权限是否允许。Loom 追求的是减少上下文搬运中的损耗，并让遗漏和变化可以被发现、核对与纠正。

让 Agent 参与建设它工作的环境

Agent 要把事情做好，就需要更接近人的实际工作环境。这里的环境包括讨论和文件，也包括团队使用的术语、操作流程、检查清单、工具、项目约定和验收方式。它们共同决定同一个任务在这个具体环境里应该怎样完成。

我们进一步探索让 Agent 参与环境建设：在执行任务时发现文档缺项、术语歧义、重复步骤或检查规则的遗漏，提出相应的整理与改进；经授权、校验和版本管理后，把确认有效的内容沉淀为文档、规则、模板或工具，供后续工作使用。人负责目标、判断与验收，Agent 协助整理、执行和维护，两者共同让工作环境变得更清晰、更可用。

由此形成一个值得长期验证的循环：从工作环境获得依据，执行任务，形成成果与反馈，经人确认后更新环境，再支持下一次工作。一个任务的价值便可以延伸到后续任务，已经澄清的条件、核实的结论和有效的方法有机会被反复采用。这为 Loom 提供了超越单次任务提效的产品方向：让持续积累的工作知识成为人和 Agent 都能使用的资产。

这些资产应当由用户掌握：哪些内容可以保存、保留多久、用于什么目的、哪些人或助手可以访问，以及如何修正、删除或导出，都需要明确的规则。群成员身份本身不等于跨任务、跨助手的数据使用许可。共享上下文必须随来源权限、参与者身份和用途边界被管理。

当前版本已保留任务来源与报告版本；长期跨任务记忆、团队共享上下文、自动维护工作环境尚未完整实现。我们会先在个人助手中验证上下文接续的价值，未来扩展多人和独立助手协作时，再同步落实相应的共享、隔离与授权机制。

以持续委托为起点，以工作成果为交付

Loom 是一款扎根真实工作环境、以持续委托为起点、以工作成果为交付的个人 AI 工作助手。它以飞书承接日常交流，以桌面工作空间提供任务管理和人工介入。用户可以明确提出一次需求，也可以设定持续生效的工作目标；在已授权的信息范围内，Loom 判断哪些事项值得处理，创建任务、调用工具、保存产物，并按用户设置完成交付。

“Loom”意为织机。消息、文件、目标和数据如同散落的线，产品的价值在于把这些线索组织起来，逐步织成报告、结论和可继续使用的工作成果。

Loom 的核心产品力，由五个相互衔接的能力构成：

  • 持续委托，让工作目标长期生效。用户可以设置“关注哪些消息、遇到什么需求、允许处理到什么程度”，并为每条委托选择观察或自动执行。后续符合条件的事件到来时，系统依据当前授权判断是否启动工作，减少反复交代同类需求的成本。
  • 上下文与任务连续，让讨论能够接上执行。每项工作分别保存目标、来源、执行记录和产物。飞书原线程、机器人私聊和 Loom 工作空间围绕同一份任务记录展开，用户可以查询、补充和继续处理，以此为起点验证更长期的工作理解积累。
  • 工具执行，让结果具备实际用途。Loom 围绕总结、数据汇总和资料查阅等场景推进工作：读取获准使用的资料，执行必要计算，记录统计口径，整理来源引用，生成报告文件。产品关注的是用户能否拿到可复核、可修改、可交付的成果。
  • 过程可见，让自主执行始终可以介入。平时助手在后台安静工作；用户进入工作空间时，可以查看实际步骤、最近动作、耗时和受阻情况，也可以暂停、接管、修改已有报告，再交还助手继续。自主程度由用户逐步决定。
  • 交付连贯，让成果回到工作发生的地方。报告可以发回飞书原线程，在机器人私聊中查询和导出，也可以仅保留在 Loom，或按照本人授权发送到绑定邮箱。报告版本与投递状态分别记录，让用户能够确认交付了哪一版、交付到了哪里。

这些能力共同形成一条完整的工作路径：表达目标或设置委托，接收工作事件，判断任务与授权，后台执行，必要时接受人工介入，最后完成成果交付。

对用户而言，改变发生在工作习惯上。可以先从少量明确的任务开始，检查助手的判断和结果，再逐步增加持续委托。助手获得更多自主权的过程，也应当是用户逐步确认其可靠性的过程。

让产品价值进入真实工作

在研发和数据分析场景中，Loom 可以承接“讨论之后还需要有人做”的整理工作。例如，研发人员在飞书中提出：“我觉得可以总结一下这几轮 benchmark，汇总一下结果。”当资料和统计范围明确、授权条件满足时，助手可以建立任务，读取指定报告，核对指标和口径，生成总结。用户可以在执行过程中检查进展，补充“重点分析可靠性问题”等要求，并沿着原任务继续。

我们的内测已经完成过多轮 benchmark 报告汇总。这一过程也暴露了值得持续优化的问题：不同报告的评分口径需要明确说明，计算结果需要能够复核，执行时间需要让用户看得见，完整报告需要与飞书中的简短结论共同交付。这些具体问题正在反过来推动产品完善。

在日常总结和纪要场景中，Loom 可以把零散记录整理成待审阅的草稿。用户在指定范围内提供工作记录，助手按“已完成、阻碍、下一步”等结构起草，并保留来源标记。用户可以在私聊或工作空间中查看、修改、导出，再决定是否交付。对于周期性工作，可以逐步通过持续委托减少重复操作。

在数据汇总和资料查阅场景中，Loom 可以承担有明确边界的处理任务。例如，对一份 CSV 按渠道汇总金额、按编号去重、排除缺失值，并保存计算依据；或者读取指定的公开资料，整理与当前问题相关的结论和引用。任务的价值既包括结果，也包括来源、口径和覆盖限制，方便用户判断是否可以采用。

这些场景具备共同特征：发生频繁、准备和整理工作较多、交付形式相对明确，同时需要保留人的判断。它们适合作为个人助手的首批落点，也能够帮助我们持续检验自主执行的可靠性。

需求持续变化，助手如何跟进

我们还制作了一个交互演示，用来展示 Loom 希望进一步探索的工作形态：Loom 群聊连续协作演示：同一个群里，接着聊 ↗。

演示围绕订单退款需求展开：产品、开发和测试在群里持续讨论，退款金额、优惠券处理、重复回调与失败重试等要求陆续补充。各自的助手跟随获准接收的讨论，更新对应的产品说明、开发方案和测试用例。它直观呈现了一个重要问题：当工作依据持续变化时，AI 如何跟上变化，减少人反复同步上下文的负担。

这份演示体现了后续的产品方向。当前实际版本优先服务单个用户；演示中的多人、多助手协同仍属于后续探索。扩展到这一阶段时，需要进一步明确每个助手代表谁、能够读取哪些信息、可以向谁交付，以及不同上下文之间如何安全协作。

对于一款承担持续工作的助手，授权与控制本身就是产品体验的一部分。用户需要能够选择信息来源、处理模式和交付目的地；系统需要在后端核验实际身份、任务归属和操作许可，并在暂停、接管或撤销授权后约束后续执行。Loom 当前已经围绕这些环节建立了相应机制，更广泛的设备隔离、跨设备执行和组织级权限仍将分阶段完善。

降低完成一项工作的总成本

这个成本包含准备资料、组织上下文、等待与跟进、纠正方向、验收结果和完成交付。只要助手能够稳定承接其中一部分，用户就能把更多时间留给业务判断、沟通和创造性工作。

我们首先聚焦在飞书中高频工作、同时承担多项整理与跟进任务的知识工作者，包括研发、产品、运营和业务分析等角色。从个人高频任务切入，有利于用明确的任务结果建立信任，再逐步扩大可委托的工作范围。

后续产品验证将围绕几项实际指标展开：需求识别是否准确，任务能否完成，成果是否被采用，用户需要介入多少次，以及完成每项有效任务需要多少时间和计算成本。上下文接续也需要单独验证：关键约束是否遗漏，变更是否可追溯，历史成果是否得到合理复用。这些指标将帮助我们判断，哪些场景能够形成稳定的使用习惯和付费价值。

目前，Loom 已形成可运行的个人助手与桌面内测版本，打通了飞书消息接入、观察与自动处理模式、任务执行、进展查看、人工控制、报告版本和交付入口。工作总结、CSV 汇总、原线程延续、私聊查询导出及本人邮箱收件等指定流程已经完成实际联调。产品仍处于早期阶段，自主识别质量、执行效率和新用户配置体验需要在更多使用中持续验证。当前本机任务依赖设备和服务运行。

Loom 的长期价值，将建立在对具体工作流程的深入理解，以及可持续维护的工作上下文之上。哪些信息值得关注、哪些决策仍然有效、什么条件下可以行动、怎样验收成果，都需要在持续工作中得到确认和修正。我们希望逐步积累的工作知识能够提高后续任务的一致性与可用性，并由用户决定其保存、复用和迁移方式。这种价值需要靠长期使用中的准确性、可维护性和成果采用来验证。

我们希望 Loom 成为用户工作环境中一个持续可用、能够参与环境建设的助手：接得住日常交流里产生的需求，接续共同形成的理解，在授权范围内推进工作，并让每一次成果都有机会成为下一次工作的依据。
