# Loom 服务端架构实施方案

Loom 采用公司集中部署：飞书应用实现用户绑定（首次使用需要引导）、功能配置和工作台（查询任务状态）入口，桌面端提供可选工作台及设备管理；DSH Agent Loop 和权威会话状态留在公司服务端。访问真实环境的适配与执行发生在目标机器的 Runner 中，服务端网关负责选择环境、授权、分发和回执。

本方案按系统架构的层次展开。目标是实现公司内部私有部署，沿用指定群和显式主人试点；逐步补齐企业身份、用户与空间权限，再扩展使用人员。通用跨群共享、跨独立 Agent 的 A2A 和共享多租户 SaaS 不进入首轮交付（由登登做功能验证，验证通过后再实施）。

## 部署基线与现有能力

| 部分 | 已有基础 | 本次架构需要补齐 |
| --- | --- | --- |
| 公司后台（后摩一体机为例，验证阶段也可选用自己的电脑） | Ubuntu ARM64 独立账号、systemd、飞书真实群任务和原线程附件；通用部署基础见 [部署说明](006-deployment.md) | 员工登录与受权限保护的产品 API、标准部署包 |
| 任务与计算 | Engine、Router、每个 Ticket 的稳定 DSH Worker Session | 场景能力绑定、可替换计算进程、跨进程独占与恢复 |
| 持久化 | 本机 SQLite、DSH 会话文件及本地产物 | 异步事务接口、PostgreSQL、DSH 外部持久化后端、独立文件存储 |
| 设备 | 同一所有者的文字讨论同步与只读召回 | 独立的远程执行协议、设备身份、Runner、执行回执和撤权 |
| 桌面端 | 管理本机运行时的 Electron 客户端 | 企业连接模式、登录、与 Runner 分离的生命周期 |

**建议的首个公司内部技术组合：**保留现有 TypeScript／Node 与 DSH；关系状态采用 PostgreSQL；产物通过 BlobStore 接口接入公司文件存储或 S3 兼容存储；持久作业和 Outbox 先放 PostgreSQL。初期可同机部署，分别管理进程、凭据与持久卷；缓存和消息通知不作为权威状态源。依赖版本在实施时固定，不引入 Kubernetes 作为首用条件。

2026-11-09 实施进展：已在 `src/execution/port.ts` 抽出并接入执行端口，覆盖本机工作区准备、原生工具／子 Agent、后台作业和停止确认；Runner 目标当前明确拒绝，禁止回退到计算服务器本机。Loom／DSH 状态仍使用现有后端，远程网关和 Runner 尚未实现。后续开发按 [工作包交接入口](work-packages/README.md) 中的 [Loom 状态外置](work-packages/LOOM_STATE.md)、[DSH 状态外置](work-packages/DSH_STATE.md)、[网关与 Runner](work-packages/GATEWAY_RUNNER.md) 分工，各包含接口、实施顺序、迁移和故障验收。

## 第一层 使用入口

### 飞书应用

一个企业应用组合机器人、交互卡片与网页工作台，继续复用 `src/sources/feishu.ts`、`feishu-trigger.ts`、`src/app/feishu-cards.ts` 和既有原线程交付逻辑。

1. 群消息由独立接入组件收取，核验应用、企业、群、实际发言人和授权范围后，持久化统一事件。先完成落库和接收回执，再异步判断与执行；不在事件回调里等待模型。按企业／应用／原事件 ID 去重。
2. 卡片提供查看、补充要求、暂停、接管、交还、审阅与下载入口。回调验证实际操作者、所属群、任务、动作许可、有效期及版本，不能凭卡片参数中的用户 ID 授权。未具备真实回调订阅时，按钮保持不可用，跳转工作台仍重新鉴权。
3. 将 `loom/src/client/live/` 的任务、进度、委托、交付物组件连接到正式产品 API。工作台页面由公司服务端提供，按飞书桌面和移动端调整布局，不嵌入原有本机管理员接口。
4. 用飞书正式登录流程换取并验证用户身份，再建立 Loom 自身登录态；需要代表用户读取业务资源时，另走资源授权。登录和访问资源的授权是两条链路，见 [飞书应用授权登录](https://open.feishu.cn/document/client-docs/build-login-free-system-)。
5. 群任务默认向原线程交付固定版本的完整附件。过程消息保持低打扰，仅必要确认、阻碍与可用结果通知；详细进展在工作台查看。

内部自建应用继续使用现有长连接接入，接入实例与 Agent Worker 独立管理，避免每个 Worker 重复启动监听器。飞书官方规定自建应用长连接回调须及时返回，当前长连接不支持商店应用；未来商店化单独实现 HTTPS 事件入口及租户安装／撤销处理，见 [长连接接收事件](https://open.feishu.cn/document/ukTMukTMukTM/uYDNxYjL2QTM24iN0EjN/event-subscription-configure-)。

**验收：**未安装桌面端的真实员工可打开应用，看到获授权的任务、进度和附件并执行允许的控制；重复事件不重复建单；未发布的卡片能力不伪装可用。落库后状态进入页面的目标延迟为 2 秒内，作为待实测目标，不作为模型完成时限。

### 可选桌面端

在 `desktop/main.cjs`、`runtime.cjs` 和首次配置流程增加“连接企业服务”模式：配置受信 HTTPS 地址、通过系统浏览器登录、读取服务端工作空间。登录使用一次性授权码及客户端校验，长期登录凭据进入系统凭据存储；网页内容不直接获得本机文件或任意进程能力。

企业模式复用产品 API 与事件订阅，提供独立窗口、通知、下载、任务介入和设备管理。设备配对和目录选择通过明确的本机操作完成。关闭窗口、退出界面、停用 Runner、暂停任务分别提供明确操作；桌面端退出不停止公司共享服务。原有本机个人模式独立保留，不能误连或迁入企业任务库。

**验收：**飞书和桌面端显示相同任务 ID、状态版本及产物；关闭窗口后服务端继续工作；退出设备连接器只影响依赖该设备的步骤；新员工不填写模型 Key 或机器人 App Secret。

## 第二层 Loom 产品服务

### 身份与资源边界

从 `src/app/loom.ts` 的本机读模型和 `task-control.ts` 的控制语义抽出应用服务。新产品 API 使用企业身份与授权中间件，原 `src/app/http.ts` 的回环管理限制保留，不能通过改写 Host／Origin 把全部 Harness 管理接口开放出去。

建立以下身份对象：企业、应用安装、用户、空间、空间成员、资源授权和设备授权。飞书外部身份按应用、企业和 open_id 组合映射为内部用户，换应用不能沿用旧 open_id；不能以显示名自动合并账号。首个实例限定一个企业；所有记录仍带企业与空间归属，以支持后续客户独立实例。

当前运行模式以整个实例的设置为边界，新架构需要将来源、授权、工具和上下文配置绑定到空间与任务。M0 先服务既有单群；M2 开通个人来源前，必须具备独立个人空间、Router／Worker 和缓存边界，不能通过给共享群 Worker 增加 Codex 工具来绕过现有隔离。

权限按四类动作独立校验：查看任务／产物、控制任务、使用资源、向目的地交付。公司管理员配置服务与连接器，不因此默认取得所有个人任务正文；群成员身份也不自动获得任务控制或其他资源权限。资源撤权同时作用于检索、缓存、预览、导出和后续模型上下文。

### 产品 API 与进度

拟提供以下接口；路径为设计约定，尚非已实现接口：

| 接口 | 用途与约束 |
| --- | --- |
| `GET /api/v1/me` | 当前身份、空间和可用动作 |
| `GET /api/v1/tasks`、`GET /api/v1/tasks/:id` | 服务端按实际身份过滤，不信任前端传入的 owner |
| `GET /api/v1/events` | SSE 推送脱敏事件，带递增游标；断线后补读，游标过期则重取快照 |
| `POST /api/v1/tasks/:id/messages` | 保存补充要求版本，随后投递原任务 Session，不直接新建聊天 |
| `POST /api/v1/tasks/:id/controls` | 暂停／接管／交还，要求预期版本与幂等键，冲突返回 409 |
| `GET /api/v1/artifacts/:id/versions/:version/download` | 鉴权后下载固定版本，默认经过服务端代理 |
| `/api/v1/delegations`、`/api/v1/devices` | 版本化委托和设备管理，写操作逐项授权 |

读操作不调用模型、不唤醒 Worker。`task-progress.ts` 的现有投影继续过滤原始推理、密钥和任意命令正文；新增排队、运行、等待资料／设备／确认、预算耗尽和投递状态。领域状态、控制状态和执行状态分别保存，页面聚合展示，不能把“接受请求”当成“Worker 已启动”。

沿用现有 `agent → taking_over → human` 及在途操作机制，扩展到远程请求。接管先持久化控制版本并阻止新分发，再取消在途工作，确认排空后显示已接管。无法确认的外部写入保留为 unknown，不能直接标记已取消；交还必须显式发起，重读人工修改并重新核验权限。

**验收：**两名用户通过 URL、搜索、导出、SSE 和卡片均不能越权；过期版本拒绝控制；接管中状态真实反映在途操作；进程重启不解除暂停。

## 第三层 Agent 计算层

### 保留 DSH 的执行主干

保留 Engine、Assessor、Executor 和稳定 Ticket；一个任务对应稳定 Worker Session，后续要求沿用该 Session。Router 以空间为上下文边界，不能把整个企业所有讨论汇入一个共同会话。DSH 计算进程可以包含多个会话，但同一会话同一时刻只有一个有效写入者。

将 `src/app/runtime.ts` 的组合拆成可部署角色：产品服务、事件接入、编排计算与 Agent Worker。初期允许同机、有限角色合并运行；先保留单空间编排者，再增加 Worker 并行，不直接启动多个现有 Runtime 共同写同一个目录。

任务运行流程：持久作业认领 → 取得 Session 写租约及代次 → 读取输入、授权、控制和场景绑定 → 恢复 DSH → 执行受控工具 → 保存事件和报告 → 释放运行权。Lease 过期或存储不可用时停止推进，不继续分发外部操作。

模型请求中断后，从已持久化边界开启后续轮次，不保证恢复原来的网络流。工具结果缺失时先查执行账本：只读或确认幂等的操作可以重试，外部写入结果不明必须核查。

### 场景路由与能力装配

新增受管理员管理的 ScenarioManifest，包含场景 ID／版本、受审阅的 Skill、工具能力及版本、输入与产物格式、运行环境要求、预算、完成校验器和允许目的地。每个任务保存 manifest 及授权快照引用，不能随着插件升级静默改变在途任务能力。

优先实现三种场景：

| 场景 | 工具与完成校验 |
| --- | --- |
| 总结与纪要 | 受控来源读取、必要时确认转写、文本／Word 生成；覆盖资料范围、来源编号与格式校验 |
| 数据汇总 | 复用精确 CSV 计算；固定去重、缺失值、金额口径及来源快照，保存复核计算产物 |
| 资料查阅 | 获准的检索与页面读取；固定引用、抓取时间和结论依据，未配置检索能力时明确等待 |

委托可明确绑定场景，模型只能从已安装且获准的候选中选择。实际工具集合取场景声明、当前模式、任务授权和执行节点能力的交集；缺能力进入等待状态，不回退到权限更大的通用 Shell。

修改 `sessions.ts` 的工具装配和 `src/executor/dsh.ts` 的工作区假设：公司 Worker 使用受限预设，禁止继承宿主通用文件、Shell、后台作业或子 Agent 执行通道。所需工具通过明确的代理适配器调用网关；内部子任务仍继承相同边界。当前的 `danger-full-access` 设置不能直接作为企业 Worker 的权限配置。

DSH 必须使用的工作区元数据目录与远端真实项目分开：服务端只保留可丢弃的临时目录，任务保存环境与资源句柄；所有涉及真实文件、目录、进程和长期作业的工具均在对应 Runner 解析与执行。不能只迁移 Bash 而把 read／write／job 等工具仍留在服务器。

**验收：**同任务连续改稿不换 Session；缺插件可见；场景绑定版本不漂移；给 Worker 注入未授权工具或网页中的越权指令会被拒绝；预算耗尽可见且停止新工作；替换计算进程后会话继续。

## 第四层 持久状态与产物

### 事务仓储改造

当前 `src/core/ports.ts` 的 Repositories、Engine 命令和 `Store.atomic` 均为同步设计，Effects、TaskControls 与部分视图还直接访问 SQLite。实施选择为：建立异步事务端口，将仓储、命令和相关调用链逐步改为 await；保留 SQLite 适配器服务个人模式，新增 PostgreSQL 适配器服务企业模式。

先以两套适配器运行相同的领域约束与故障测试，再切换企业实例。一个命令事务内保存聚合变化、作业／Outbox 意图和幂等结果；模型调用、文件上传、飞书发送及设备执行均在提交后进行。`afterCommit` 只用于可丢失的唤醒，可靠工作必须进入持久作业表。

### 状态归属与表组

| 存储组 | 保存内容及关键约束 |
| --- | --- |
| 身份和授权 | 企业、安装、用户、空间成员、资源／设备授权及修订版本 |
| 任务领域 | Trigger、Thread、Decision、Ticket、Assignment、要求版本与委托 |
| DSH 会话 | Session 元数据、连续 seq 的事件、格式版本、任务关联与投递 requestId |
| 运行与控制 | 持久作业、会话租约、控制版本、在途请求、等待条件、运行预算 |
| 工具执行 | 环境、能力、工具请求、执行回执、结果哈希、外部操作未知状态 |
| 产物和交付 | 产物版本、来源快照、可见范围、文件指针、Outbox、发送回执 |
| 审计和投影 | 关键授权／控制／工具事件、脱敏进度及消费游标；不复制完整推理到产品日志 |

唯一约束覆盖来源事件、Session 事件序号、任务输入投递、工具请求与产物版本。作业通过短事务认领后提交，再执行长工作；采用租约及代次处理进程失联。可以用 `FOR UPDATE SKIP LOCKED` 避免多个作业消费者互相等待，但它不替代 Session 写租约、任务权限或严格顺序控制，见 [PostgreSQL SELECT 文档](https://www.postgresql.org/docs/current/sql-select.html)。

### DSH 外部会话后端

通过已安装的 `@deepseek-ai/dsh-session-persistence` 服务实现 PostgreSQL provider，遵守 `create/open/read/append/stat/list/flush/close` 约定、连续 seq、格式门禁及单写者要求。使用已有共享契约测试；需要的测试辅助若未随发布包分发，则在对应上游源码版本验证，不假设运行包包含测试模块。

写所有权由数据库租约及递增 fencing 代次保证，所有追加与后续分发检查当前代次，旧进程无法在新持有者接手后继续写。后端实例按企业范围绑定，产品查询再按空间与实际用户过滤；底层无过滤的 `list()` 不向员工直接开放。`flush` 成功才视为持久性屏障，不能以客户端收到流式文本代替。

同时盘点 DSH 的 Workspace 注册、会话索引、待处理 Inbox、附件引用、预设／Skill／插件版本及模型配置。需要持久化的数据进入相应后端；可重建配置来自固定发布包和服务端配置，附件进入 BlobStore，真实后台作业由 Runner 追踪。本方案中的服务端临时目录不承载远端真实项目，Workspace 与 Session 的稳定关联须在适配中保存或重建，不能仅替换会话文件后端就宣布完全无状态。M1 必须从没有旧本机目录的新 Worker 恢复任务，才算通过。

输入投递先保存 requestId，再注入 Session 并 flush，最后确认投递。崩溃后检查已持久事件中的同一 requestId，避免重复注入；任务库与会话日志的两个提交点靠持久意图和幂等补齐，不能假设它们天然原子。工具调用与回执也使用稳定请求 ID 关联，恢复时先核查真实结果。

### 文件和版本

给 `artifacts.ts`、`result-delivery.ts` 和文档渲染结果增加 BlobStore 端口。先保存临时对象并验证完整性，再提交不可变版本和文件指针；清理未引用的临时对象，不覆盖既有版本或人工改稿。

每个版本保存原始字节的 SHA-256、长度、媒体类型、来源与可见范围。对象存储 ETag 不能直接作为完整文件哈希；例如 S3 分段上传的 ETag 并非整文件 MD5，见 [S3 Object 文档](https://docs.aws.amazon.com/AmazonS3/latest/API/API_Object.html)。实际字节校验以应用保存的哈希及相应存储校验能力为准。

默认通过鉴权下载代理读取固定版本。短期预签名 URL 如后续启用，应明确其有效期内的撤权窗口，不能当作即时撤权方案。定稿与交付分开：只有固定版本通过来源、权限、控制和目的地复核后进入 Outbox；结果不明的发送不自动重发。群任务回原线程，个人来源产物默认只在本人工作台可见，向群或邮箱交付另行授权。

备份覆盖业务库、DSH 事件、文件对象和版本清单；凭据及恢复所需密钥独立加密管理。明确音频、源文本、会话、日志、导出及备份的留存／删除策略，不能把删除 UI 记录当成删除全部副本。既有飞书文字同步继续作为来源连接器，不充当这套权威存储。

**验收：**在任务输入、工具调用、产物提交和发送前后分别杀进程；恢复后同一任务可续接，已持久记录不丢失，未知写入不重复发起。竞争写入、存储故障、旧代次结果和损坏文件被拒绝。备份在隔离实例恢复后能核对任务、会话、产物及哈希。

## 第五层 工具路由与设备网关

### 设备与环境注册

建立环境注册表：环境 ID、所属企业／所有者、获准空间、设备身份、已安装能力与版本、在线状态、并发容量和最近心跳。环境名称与在线状态本身不构成授权。

用户在已登录页面创建短时、单次的配对许可；Runner 在本机生成设备密钥，配对绑定用户、企业、设备公钥和允许范围。使用 TLS 保护主动出站的 HTTPS／WebSocket 连接，设备凭据可独立轮换与撤销；公司执行节点采用管理员配置的服务身份。无需开放个人电脑的 SSH 或远程 Shell 入站端口。

### 请求与回执

协议固定版本并验证输入，至少包含：

```text
ToolRequest
  protocolVersion, requestId, tenantId, spaceId
  taskId, assignmentId, sessionId, environmentId
  toolName, toolVersion, args, argsHash
  grantId, grantRevision, controlRevision, executionEpoch
  idempotencyKey, effectKind, expiresAt, timeoutMs, maxOutputBytes

ToolReceipt
  requestId, environmentId, executionEpoch
  state, startedAt, finishedAt, resultRef, resultHash, safeErrorCode
```

网关生成身份、授权与控制字段，模型只提出受 schema 约束的工具意图。资源使用受授权的句柄，不能让模型通过任意路径或设备名称选择环境。Runner 校验调用来源、设备、工具版本、许可、路径及参数后才执行；同一 requestId 的参数哈希不一致必须拒绝。

服务端与 Runner 都维护执行记录。重复投递已完成请求只返回既有回执，不重跑。重连后先对账 accepted／running／unknown 请求，再决定是否补发；后台长作业返回稳定 job ID，进度和取消都经过同一网关。

### 离线与接管

设备不在线时持久保存等待条件并释放 Agent 运行名额，设备上线后唤醒任务，重新核验来源、授权、控制、预算和依赖。过期请求不因设备重连直接执行。

对外写入在执行前在线取得一次性许可并登记在途操作；连接失效后 Runner 不启动新的写入。控制修订与执行代次约束后续请求及结果提交。已经获准且进入执行的操作可能在断线后完成，分区下不能承诺即时撤回：以取消回执、外部查询或人工核查确认，页面保留不确定状态。租约和 fencing 能防止旧请求继续被接受，但不能撤销已经发生的外部副作用。

**验收：**两台 Linux 注册到同一企业后只可使用各自授权资源；撤销设备后无法重连或接新调用；离线不空转模型；旧请求、重复请求、改参数请求、接管后重放和未知写入均按约定处理。

## 第六层 环境适配与实际执行

### 公司受管执行节点

独立 Runner 提供受控飞书读取、CSV 计算、Word 渲染、检索和后续内网连接器。复用 `skills/dsh-superagent-office/aggregate.py`、`src/document-render.ts`、`src/asr-bailian.ts` 等现有能力，将它们包装为有 schema、版本、权限与完成校验的类型化工具，不将“安装插件”解释为开放全部 Shell。

文档生成采用受管渲染作业，产物上传 BlobStore 后由产品服务登记；DSH 仍通过受控报告工具提交要求，不直接读取服务器任意文件。工具需要外部凭据时由所在节点的凭据代理注入，模型只获得资源句柄和受限结果。

执行节点可与服务端同机，但使用独立账号或容器及明确的目录挂载、网络出口、CPU／内存／时间与输出限制。运行不可信代码需另设沙箱，不能把工作目录或 TypeScript 工具守卫当作 OS 隔离。内网数据连接器还需资源 ACL、查询范围和输出范围，不依靠网络可达性授权。

### 个人电脑上的 Runner

先实现 Linux 无界面的用户级服务，再分别完成 macOS 和 Windows 原生服务与签名安装验收。Runner 只保存设备凭据、目录／工具授权、必要的幂等回执和本地环境，不保存完整 Loom Session；本地执行账本采用 SQLite，配合系统权限和有界保留。

第一批只开放三个能力：健康与能力检查、获准目录的只读访问、本人 Codex 历史的限定读取。复用 `src/app/codex-history.ts` 和 `src/codex-rpc.ts` 的过滤与分页逻辑，改由 Runner 调用已安装的只读来源接口；请求绑定本人、项目／会话、日期和用途，分批传回必要来源快照。目录读取与允许内容进入服务端／模型分别确认，不同步整台电脑，也不恢复或控制 Codex 原生会话。

目录授权使用资源句柄映射本机根目录，拒绝路径穿越、越界符号链接和配置／凭据目录；必须考虑检查到打开文件之间的竞态。后续文件写入采用前置哈希或版本检查，冲突保留人工改动；命令执行采用审阅过的能力、受限 argv／工作目录和进程组取消，再按场景补齐沙箱。

个人来源的结果默认仅本人工作台可见。在群内触发也不能自动把私人历史送入群 Router 或结果附件，只有完成 F1 的来源及目的地授权后才能开通相应跨来源交付。

**验收：**真实第二台 Linux 读取获准的虚构材料；来源越界、符号链接和撤权拒绝；必要文字经批准进入服务端后可完成日报，源设备离线后已上传材料仍可用；断线写入不确定性如实显示。macOS／Windows 仅在各自真实系统测试后标记支持。

## 第七层 模型推理服务

保留 DSH 模型路由，将模型调用配置与用户桌面安装分开。管理员配置 API 服务或私有模型、凭据引用、可用模型和数据出站政策。Agent Loop 在公司服务器运行不代表推理也在公司内部；外部模型、ASR 与其他外部工具各自明确数据去向。

Router 和 Worker 可按场景分别绑定模型配置，记录版本、耗时、token、失败类型和预算。重试有次数、总耗时与费用上限；不确定外部工具写入不因模型重试重新执行。模型切换先核验工具调用、结构化输出和预算配置，再作用于后续运行，不重算历史产物。当前模型不因本方案自动更换。

**验收：**模型超时、限流、余额不足和服务故障在进度中可见且有退出条件；密钥不进入浏览器包、Runner 普通诊断包、模型正文或产物；禁止出站的资源不会被外部模型或 ASR 使用。

## 横向运维与迁移

交付版本化的服务端安装包及 Compose／systemd 配置：产品 HTTPS 入口、接入与 Worker 进程、数据库、BlobStore 配置和独立 Runner 包。数据库和内部管理不对员工网络直接开放；设备连接只接受经过认证的专用协议。模型与应用 Secret 通过私有引用加载，不放进镜像和安装包。

持续记录企业／空间／任务／Session／请求／环境的关联 ID，监测接入落库、排队、模型、工具、等待设备和投递各段耗时，避免只看到“已接受”。Watchdog 检查进展与租约，遵守人工停止；不通过重启解除接管，不把临时模型故障无限重试。

迁移步骤为：暂停新接单 → 排空或明确冻结在途动作 → 一致备份 SQLite、DSH 与产物 → 向新存储导入并保留 ID／版本／控制状态 → 核对来源与归属 → 隔离只读校验 → 经后续部署安排切换单一写入者。全程不双向双写；回退前检查 schema 兼容性和切换后的新增数据，不用旧库覆盖新任务。个人实例不自动迁入公司实例。

| M2 端侧只读执行 | 个人空间隔离、设备网关、Linux Runner、只读目录／Codex 适配、等待设备 | 两台真实 Linux、配对与撤销、越界拒绝、共享群无法召回私人来源、离线唤醒及本人工作台日报全链路 |

| M4 企业交付 | 安装向导、升级回退、运维指标、留存策略、各平台发行 | 空白环境安装、依赖与权限预检、升级后任务保留、备份演练、签名包与真实员工验收 |
