# 团队工作助手：飞书入口 + 服务器部署（设计稿）

2026-11-09 按用户要求起草，同日开始实现阶段 1 的本机原型（见下文「原型」）。原型使用模拟飞书，不连接真实机器人、不向团队开放；本文不构成部署、开通权限或向团队开放的授权，各阶段上线前须按本文和 [ROADMAP](ROADMAP.md) 的对应条目补齐实现与验收。

## 背景与范围变化

当前版本面向单个用户：一个飞书机器人、一个 DSH profile、一份任务库，`ownerOnly` 只接受本人消息，Worker 在本人电脑上执行，能接触本机文件、本人的 lark-cli 用户登录、Codex 历史和 BugFixer 等本地资源。

目标是改为团队共用的工作助手：

- 入口只有飞书：私聊机器人、在群里和机器人对话，后续可加飞书网页应用。
- 服务全部部署在服务器上，任务、session 和产物都在服务器端生成，通过对话交付；整体与任何人的本机解耦。
- 按飞书身份区分用户，第一次对话时自动为其新建个人工作区。
- 群聊默认私下回复本人，只有判断为给群里所有人看的结果才发到群里。

这属于 AGENTS.md 所说的范围变化：从单用户扩展到多用户，并引入服务器端执行。因此 ROADMAP 中 F1（多用户与共享空间）、P2/P4 中的执行隔离与交付检查、"跨设备与更广泛的安全边界"中云端计算一节，均纳入本设计的验收，不再视为后续可选项。跨独立 Agent 委托（F2）和远程设备执行仍不在范围内。

## 目标与非目标

目标：

- 团队成员各自拥有隔离的工作区：任务、session、产物、规则和用量互不可见。
- 复用现有的任务 / Worker / 报告 / 回复出口、暂停 / 接管、产物版本等核心逻辑，不重写引擎。
- 任一用户的消息、文档或网页内容都不能让系统越过其工作区边界。
- 对一个几十人的团队可运维：自动开通、休眠、停用和清理。

非目标（本轮不做）：

- 共享项目空间内的多人协同编辑；首期只有"个人工作区 + 群聊公开结果"两种可见范围。
- 跨租户、外部联系人使用。
- 代替成员执行需要其个人授权的飞书操作（日历、文档、邮件），放到第三阶段。
- 本机能力：Codex 本机历史、桌面客户端、本机 BugFixer 桥接、个人人设等不随迁。

## 总体结构

```
飞书事件（长连接） ──> 网关 ──按 union_id──> 工作区 A（容器：DSH + 任务库 + 产物）
                       │                 └> 工作区 B（容器）
                       │                 └> …（首次对话时创建，空闲时休眠）
                       └<── 各工作区的发送请求（经网关统一检查后发出）
```

### 网关

一个常驻进程，唯一持有飞书应用凭据和事件连接。现在的实现由单个 DSH 通过 `lark-cli event consume --as bot` 消费事件（`src/sources/feishu-loops.ts`），一个应用只能有一个消费者，所以多实例时必须由网关统一消费再分发。职责：

- 解析发送人身份，查找或创建工作区，把事件转给对应工作区；工作区休眠时先唤醒再投递，投递按事件 ID 去重。
- 统一出口：工作区不直接持有机器人凭据，发送消息、上传文件、加表情回应都向网关提交请求；网关按下文"群聊回复规则"检查目的地后再发出，并保留发送回执。
- 准入、配额、停用和审计都在网关执行，不依赖工作区内的提示词。

### 工作区

每个用户一个，运行在独立容器中：

- 独立的 DSH_HOME、状态目录、任务库和产物目录，沿用现在"一个 profile 一个目录"的隔离方式，只是从本机目录换成容器卷。
- Worker 只能看到本工作区的目录；CPU、内存、磁盘、进程数有上限；默认无出站网络，按需对模型接口、检索服务等白名单放开。
- 不持有飞书 App Secret、其他用户的数据或宿主机凭据；需要的外部能力通过网关或凭据代理提供。
- 空闲一段时间后休眠（停止容器、保留卷），收到消息再启动；长时间运行的任务在休眠判断中视为活动。

选择"每人一个实例"而不是把代码改成单进程多租户：现有代码处处假设只有一个所有者，按实例隔离可以基本原样复用，隔离边界也由容器保证而非逐处加 `workspace_id`。代价是资源占用更高；几十人规模可接受，人数增长后再评估合并。

## 用户身份与工作区开通

- 飞书消息事件的发送人信息中带有 `open_id`、`union_id`，申请通讯录相应权限后还带 `user_id`；接入时以实际事件核验字段。
- 工作区主键用 `union_id`：同一开发者的不同应用下保持不变，以后换应用或加应用不会让工作区"失联"。同时记录 `open_id` 用于向本人发消息（当前代码和名单均以 `open_id` 标识人，迁移时改为以 `union_id` 为主键）。
- 首次对话自动创建工作区，前提：
  - 飞书后台的应用可用范围只开放给团队成员；
  - 网关拒绝外部租户的发送人（事件中的租户信息与本企业不符）；
  - 可选的管理员名单 / 部门白名单，未通过时回复一条说明而不创建。
- 创建时初始化目录、默认规则和用量额度，私聊发一条欢迎说明（能做什么、数据存在哪里、如何删除）。
- 群聊中第一次 @ 机器人的成员同样创建工作区；群本身不拥有工作区。

## 群聊回复规则

一条群消息产生的任务属于发消息的人的工作区。结果的可见范围按以下规则决定，由网关在发送前强制执行：

1. 默认私下：在群里给原消息加一个表情回应表示已收到，进展和结果私聊发给本人。飞书支持在群里发送仅指定成员可见的消息卡片，可作为备选确认方式；当前配置为纯文字回复，启用前须核验接口和权限。
2. 公开发到群里，仅当以下之一成立：
   - 请求中明确要求发到群里（如"发到群里""给大家总结一下"）；
   - 任务内容本身来自该群、面向该群（如群聊总结）。
3. 公开结果只能使用该群成员都能看到的信息：本群消息、公开资料，以及本次请求中发起人明确提供的内容；不能引用发起人个人工作区中的其他会话、记忆和产物。工作区在提交公开发送时须附上本次结果的来源，网关据此拒绝含有私有来源的公开发送并改为私聊。
4. 群里默认只在 @ 机器人或叫名字时触发。当前个人版的"群聊监听全部 + 自动执行"在多人群里会让每人每句话都触发一次判断，成本和误触发都不可接受；如需对某个群开启，由管理员按群单独配置。

规则 3 是关键约束：模型对"是否给所有人看"的判断可能出错，但即使误判为公开，发出的也只能是群成员本来就能看到的信息。

## 产物与交付

- 短结果直接发文字消息。
- 长报告或文件：上传为文件消息，或生成飞书云文档并只共享给本人；两者都需另行申请权限，经网关发出。
- 产物不可变版本、来源哈希、人工修改后 Worker 须基于最新版本继续等现有规则（`src/app/artifacts.ts`）在工作区内照用。
- 网页端暂不提供；后续如需查看任务和产物，做成飞书网页应用并用飞书免登录确定身份，只展示本人工作区，替换现在的 token 链接。

## 凭据与外部操作

- 飞书 App Secret 只在网关；工作区通过网关的受控接口发送和读取，不把任何密钥注入模型上下文、产物或日志。
- 模型接口密钥由网关或凭据代理注入请求，工作区内不可读取。
- 读取群历史、拉取消息中的图片和文件时，网关只返回发起人所在、且机器人在其中的会话内容。
- 第三阶段如需代表成员操作其日历、文档、邮件，由成员本人授权，用户令牌按工作区加密保存并续期，撤销授权后立即失效；不复用任何一个人的登录。

## 配额、运维与数据生命周期

- 用量：按人设每日模型调用和费用上限、并发任务数，超额时私聊告知；网关记录每次调用的归属。
- 停用：成员离职或被移出可用范围时，根据通讯录变更事件停用工作区，停止在途任务、作废排队发送；保留期满后删除数据。
- 删除与导出：本人可在私聊中请求导出或删除自己的工作区；删除覆盖任务、产物、索引、缓存和日志中的正文。
- 审计：网关记录开通、停用、发送、外部写入和管理员操作，日志不含消息正文和密钥。
- 备份：工作区卷定期备份，恢复后已发送的消息不重复发送（沿用现有发送回执与去重）。

## 从当前代码迁移

可以原样复用：任务 / 指派 / 报告 / 回复的核心引擎（`src/core/`）、产物版本、暂停 / 接管、提示词和办公类 Skill。

需要改造或新增：

| 部分 | 现状 | 改为 |
| --- | --- | --- |
| 事件消费 | 单个 DSH 直接消费飞书事件 | 网关消费，按工作区转发 |
| 发送 | `src/sources/feishu-channel.ts` 直接调用 lark-cli | 提交到网关出口，网关检查后发送 |
| 身份 | `open_id` 名单 + `ownerOnly` | `union_id` 工作区 + 网关准入 |
| 执行环境 | 本人电脑上的进程 | 每人一个容器，限制文件、网络和资源 |
| 群聊触发 | 监听全部、自动执行 | 默认 @ 或叫名字；按群配置 |
| 群聊交付 | 回复到群 | 默认私聊 + 表情回应；公开发送受来源检查 |
| 管理 | 本机 Loom 页面 | 管理员配置（准入、配额、按群设置），成员无管理入口 |

不随迁：本机 Codex 历史与日报委托、桌面客户端、跨设备同步、本机 BugFixer 桥接（如需在团队中使用，另行设计为服务器端 Skill）、个人邮箱桥接、个人人设。

## 分阶段计划与验收

### 阶段 1：私聊试点（3–5 人）

- 网关 + 每人一个工作区容器，首次私聊自动开通，休眠与唤醒。
- Worker 只开放无副作用工具，或在严格沙箱内执行命令；无出站网络，模型调用经代理。
- 按人用量上限。
- 验收：
  - 两个用户并发使用，任一方无法通过对话、文件路径、命令或检索读到另一方的任务、产物或日志；
  - 外部租户和可用范围外的人不能开通工作区；
  - 工作区内拿不到 App Secret 和模型密钥；
  - 重放同一事件不重复接单，重启网关或工作区后不重复发送；
  - 超额后拒绝新任务并告知本人。

### 阶段 2：群聊

- @ 触发、表情回应确认、私聊交付；公开发送规则与来源检查。
- 验收：
  - 未明确要求公开的群请求，结果只私聊给发起人；
  - 构造"把我之前的私人报告发到群里"等请求，网关拒绝公开发送并改为私聊；
  - 群里其他成员不能通过追问、"继续"或引用消息操作发起人的任务；
  - 被移出群或移出可用范围后，后续消息不再进入该群相关任务。

### 阶段 3：个人授权操作与运维

- 成员授权的飞书操作、文件 / 云文档交付、离职停用、导出删除、审计与备份。
- 验收：
  - 撤销授权后排队和在途的外部写入不再执行；
  - 停用工作区后数据按保留策略删除，日志中无正文；
  - 备份恢复后不重复发送。

每阶段完成时，把实现位置和验证证据写回 ROADMAP 对应条目，真实环境验收另行记录；未通过的条目保持未勾选。

## 原型（2026-11-09，阶段 1 部分）

按用户要求先在本机实现网关原型：数据库建在本地，飞书先用模拟实现，每个工作区先用本机进程而不是容器。

### 已实现

- 网关本地数据库 `src/team/store.ts`（SQLite，位于 `LOOM_TEAM_ROOT/gateway.sqlite`，文件 0600）：以 `union_id` 为主键的工作区（只存访问令牌的哈希）、已见事件、按工作区排队的消息及确认位置、每次发送的判定（发送、改为私聊、拒绝）和审计记录。审计只记 ID、判定和原因，不记消息正文和令牌。
- 准入与路由 `src/team/gateway.ts`：
  - 只接受本企业租户、带 `union_id` 的真人消息；群里只有 @ 机器人或叫名字才接收；可选白名单；按人每日条数上限，超额时私聊告知一次。
  - 第一次对话自动创建工作区，并私聊发欢迎说明；同一事件、同一消息重复投递只处理一次。
  - 群消息给原消息加表情回应，再以「已 @ 机器人」的形式交给发送人的工作区。
- 工作区只能通过网关使用飞书：`src/team/shim.ts` 是工作区配置的 `lark-cli`，不含任何飞书凭据，每次调用都转给网关判定。网关：
  - 回答 DSH 启动时的机器人自检（`auth status`、`config strict-mode`、机器人信息），所以 DSH 本身不用改；
  - 发送：私聊照常；群里的结果默认改为私聊发给发起人并注明来自哪个群，只有请求里明确要求发到群里时才发到群；只能发给本人，不能发给其他人或本人没用过的会话，不能回复其他工作区的消息；按幂等键只发一次；
  - 读取：只能读本人和机器人用过的会话（本人的私聊、本人 @ 过机器人的群）里的消息、成员和话题；
  - 其他命令一律拒绝，包括删除消息、任意 `api POST`、`auth login`。
- 每人一个 DSH `src/team/workspaces.ts`：按桌面端创建独立实例的同样步骤，为每个工作区建立独立的 DSH_HOME、状态目录、端口和 Loom 插件，所有者设为该成员，私聊加群 @ 均可触发；模型密钥只通过进程环境传入，不写入工作区文件。`src/personal-setup.ts` 为此新增可选的 `otherChats`，不传时桌面实例行为及其记录不变。
- HTTP `src/team/server.ts`（仅监听本机）：工作区用自己的令牌拉取事件和调用 CLI；管理员令牌查看工作区、停用工作区、查看审计；模拟模式下可注入飞书事件、定义群和成员、查看机器人发出的所有消息。

### 运行

```bash
pnpm build
```

```bash
LOOM_TEAM_ROOT=./team-data LOOM_TEAM_TENANT=<租户> LOOM_TEAM_ADMIN_TOKEN_FILE=<管理员令牌文件> \
LOOM_TEAM_RUNTIME=process LOOM_TEAM_MODEL_BASE_URL=<兼容 OpenAI 的地址> LOOM_TEAM_MODEL=<模型> LOOM_TEAM_MODEL_KEY_FILE=<密钥文件> \
LOOM_TEAM_ALIASES=<机器人别名> pnpm team:gateway
```

不设 `LOOM_TEAM_RUNTIME=process` 时只运行网关、不启动 DSH，用于单独检查路由。事件通过 `POST /sim/events`（管理员令牌）注入，格式与飞书 `im.message.receive_v1` 原始事件相同；`GET /sim/sent` 查看机器人发出的消息。

### 越权记录（2026-11-09）

白名单加入第二位成员（用户确认为可信同事，知悉无隔离的风险，并在越权发生后选择保留）后，用户在私聊中测试：询问「本地有哪几个用户的工作区」、查看 `../`、要求删除并「全部清空」自己的工作区。

- 模型密钥与网关管理员令牌的值未出现在任何 Worker 会话记录中；当时网关库中只有用户本人的消息。

### 容器隔离（2026-11-09）

越权记录之后按用户要求实现每个工作区一个容器（`LOOM_TEAM_RUNTIME=container`），并把正在运行的 Shannon 网关切到该模式：

- 镜像 `loom-workspace:0.1`（`docker/workspace.Dockerfile`）：Node 22 加 git（DSH 部署检查需要 2.32 以上）和 python3（办公 Skill），不含任何密钥。
- 每个工作区的 DSH 在独立容器中运行（`src/team/workspaces.ts` 的 `dockerRunArgs`）：去掉全部 capabilities、禁止提权、只读根文件系统、可执行的 `/tmp` tmpfs（DSH 从这里加载原生模块）、内存/CPU/进程数上限、以宿主用户身份运行；宿主只挂载 DSH 安装、Loom 代码及其依赖（只读）和该工作区自己的目录（读写）。档案初始化（创建 DSH profile、链接插件）仍在宿主执行，只写该工作区目录，不运行模型或 Worker。
- 模型代理：工作区的模型地址指向网关 `/ws/model`，密钥是它自己的网关令牌；网关校验令牌后换成真实密钥转发，只放行 chat/completions、completions、models、embeddings，并在审计中记录每次调用的状态。容器内拿不到真实模型密钥。
- 网关额外监听 Docker 网桥地址，只提供 `/ws/*`；管理和模拟接口仍只在本机回环。网关停止时按名称停止所有工作区容器。
- 隔离验证（模拟飞书，两个容器化工作区，2026-11-09）：
  - Alice 的容器内只能看到自己的工作区目录，看不到 Bob 的；网关数据库、模型密钥、管理员令牌、个人版数据、机器人 CLI 配置、`~/.ssh` 均不存在；代码目录只读；只看到容器内 7 个进程；环境变量中没有真实模型密钥。
  - 容器访问宿主回环上的网关管理接口失败，经网桥访问管理接口返回 404；无法连到 Bob 容器的 DSH，也无法连到宿主仅监听回环的服务。
  - DSH 只经代理调用模型（两次 200），回复经网关发出。
  - `tests/team-gateway.spec.ts` 新增：容器参数（无 capabilities、只读根、只读挂载、仅自身目录可写、限额）；模型代理用真实密钥转发、错误令牌 401、未列出的路径 404、网桥上的管理接口 404。全量 1390 项通过。
- 测试过程中维护者的一次清理命令误停了正在运行的 Shannon 网关（14:45:22–14:45:35，约 13 秒），随即恢复；期间的消息可能未送达。

### 菜单看板（2026-11-09）

用户点机器人自定义菜单（动作选「推送事件」）时，网关私聊回一张只读的任务看板卡片：

- 网关另起一个 `lark-cli event consume application.bot.menu_v6` 消费菜单事件（`src/team/lark.ts`，与消息事件同样断线重连）。菜单事件带 `operator_open_id`、`operator_union_id` 和 `tenant_key`。
- `Gateway.menu`（`src/team/gateway.ts`）：按事件去重；配置了租户时校验租户；白名单校验点击者；按 `union_id` 或 `open:<open_id>` 找到工作区，并要求工作区所有者就是点击者；卡片只发给点击者本人，只含其自己工作区的数据。没有工作区的人收到「先私聊我一句话」的提示；发送失败时撤销去重记录，飞书重投时可重试。
- 看板内容（`src/team/board.ts`）：网关在宿主上以只读方式打开该工作区的 `state/orchestrator.sqlite`，把任务分为「等你处理」（有待回答的问题、受阻或失败）、「进行中」（运行、排队、等待）和「最近完成」（7 天内结束，最多 5 条），并附今日消息数和模型调用数。任务标题和摘要中的 Markdown 符号按原文显示。工作区本身不参与，也无法扩大看板读取的范围。
- `event_key` 中含 attention/todo/待 只显示等你处理，含 running/进行 只显示进行中，含 recent/done/完成/产物 只显示最近完成，其他键显示全部。刷新方式是再点一次菜单；卡片上没有按钮，卡片回调仍未接入。
- 每次发送卡片记入网关发送记录和审计（`menu_board`，只记 event_key 和视图）。模拟模式新增 `POST /sim/menu`。
- `tests/team-gateway.spec.ts` 新增 4 项：只读读取和分组、只发给点击者且只含本人数据并去重、租户/白名单/无工作区、发送失败可重试；`LarkFeishu.sendCard` 使用 `--msg-type interactive`。

### 与设计的差距（仍未完成）

- 真实飞书只接了消息和菜单事件；卡片回调、群成员变化等事件未接，工作区以 `open_id` 而非 `union_id` 为键，也没有租户校验（由白名单代替）。
- 隔离仍不完整：容器仍可经网桥访问外网和宿主上监听所有地址的服务；Loom 代码和依赖以只读方式对容器可见；用户态 Docker 不是虚拟机级隔离。出网白名单、独立网络和更严格的内核隔离（如 gVisor）待做。
- 公开发送只检查请求措辞，还没有检查结果的来源是否都对群可见（设计中的规则 3）。
- 没有休眠：工作区启动后一直运行，直到网关停止。
- 文件只登记文件名和大小，不上传内容；卡片回调不路由。
- 工作区的「本人会话」以网关路由过的消息为准，还没有向飞书核对群成员是否仍在群里。

## 待决问题

- 服务器与容器方案：单台服务器 + Docker，还是现成的容器平台；容器镜像如何随 DSH 版本升级。
- DSH 在容器内的 Harness 界面是否保留给管理员排障，访问方式如何保护。
- 模型费用的承担与额度：统一账户按人限额，还是按部门分摊。
- 是否需要"项目空间"（多人共享一个工作区）；如需要，按 F1 单独设计成员、资源和控制权。
- 数据保留期限与公司合规要求。
