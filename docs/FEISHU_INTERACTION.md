新应用仍等待企业审批；本轮继续使用“个人助手机器人”的现有权限，不切换应用，不扩大监听范围。现有原线程追加要求、本地任务控制的实际验收仍见 [PERSONAL_ACCEPTANCE.md](PERSONAL_ACCEPTANCE.md)。

## 任务持续存在，执行可以在后台

面向用户保留稳定的任务会话：一件事有一个任务 ID、目标、来源、当前要求、产物和控制记录。底层 Worker 可以重启或更换，用户仍进入同一件事。打开或查看任务不暂停执行；发来新的要求也不自动解除人工暂停或接管。

已确定两个互通的入口，不以新增工作台作为使用前提：

| 入口 | 用户在这里做什么 | 展示边界 |
| --- | --- | --- |
| 群内原线程（主入口） | 发起一件事、补充要求、阅读结果，按需展开进展、依据和控制操作 | 延续该任务，不把其他任务、私人笔记或个人总览带入群 |
| 机器人私聊（按需入口） | 查我的任务、草稿和产物附件，处理个人决策及交付设置，跳回原线程 | 只向所有者展示自己的任务；查询不启动、重开或暂停任务 |

两个入口连接同一任务，不生成彼此独立的工作副本。当前以文字命令查询和控制，卡片按需展开仍是设计目标；私人报告在私聊呈现，本地 Harness 面板保留为开发与运维入口。群是资料和交付渠道，不因此变成多人共享助手。飞书网页／工作台仅保留为以后需求明确时的备选方案。

当前私聊支持“我的任务”“我的产物”“查看工作总结进展”，也可用 `/助手 产物 任务ID` 和 `/助手 导出 任务ID`。返回持久报告与真实 TXT 附件，不新建任务。当前不支持任意文件取回、任务卡片或所有自然语言表达；多个同名任务须复制列表中的唯一 ID。卡片、原线程跳转及原生附件索引仍按后续目标推进，不把本机文件路径当成可用下载链接。

## 通知与静默发现

- 原线程的任务摘要只保留当前阶段、已确认的进展和下一步；普通阶段变化优先更新原摘要，不逐步刷屏，也不展示模型内部推理。
- 主动消息用于可用结果、必须由用户决定的问题、执行失败或确实无法继续的阻碍。用户主动查看时可见详细活动。
- observe 模式发现的候选只供所有者主动查询；不自动接单，不在群里询问，也不启动 Worker。候选显示依据、建议交付物和为什么可能值得做，用户可选择发起或忽略。
- 不把“一次点击允许做这个任务”扩大为长期自动执行规则。后续预授权需要单独定义信息范围、动作、预算和交付目的地。
- 汇总入口区分“需要你决定”“正在处理”“结果可用”；具体任务页面再分别显示执行阶段与控制权，避免用“运行中”掩盖暂停、交接或结果不明。

## 介入的交互语义

| 动作 | 预期反馈 | 后台约束 |
| --- | --- | --- |
| 查看进展／依据／产物 | 展开详情，任务按原状态推进 | 不创建新任务，不唤醒已结束的 Worker，不改变控制权 |
| 补充要求 | 保存为本任务的新要求，显示已记录及是否等待继续 | 记录要求版本；旧结果需要重新核对，不得作为满足新要求的成果交付 |
| 暂停 | 先“正在暂停”，受管操作停止后才显示“已暂停” | 阻止后续工具、作业及排队交付；恢复须显式发起，重启不解除暂停 |
| 接管 | 先显示当前在途操作与“正在交接”，停止确认后“已接管” | 实际操作未结束不能宣布交接；已发生的外部操作不会自动撤销 |
| 编辑草稿 | 接管后开放编辑；保存保留人工版本 | 未接管时先申请接管；后台不能覆盖人工版本；编辑冲突须显式处理 |
| 交还助手 | 提交交接说明，助手重新读取当前要求与人工版本 | 仅在交接完成后允许；使旧排队结果失效，保留人工改动后继续 |
| 结果不明 | 停留“待核查”，列出具体操作和本地核查入口 | 查询失败、客户端取消或重启都不能证明外部动作未发生；核查完成前不得自动恢复或重放 |

控制卡片的按钮应携带服务端可核验的任务和状态版本，隐藏实现字段。失效卡片提示“状态已变化，请刷新后重试”；不能用旧的“继续”按钮解除新的暂停。只允许所有者操作，转发卡片或填写他人姓名不能获得权限。文本入口先使用明确的命令与服务端身份检查，不让模型从普通讨论中直接执行控制。

此前原型中的编辑、保存和线索转任务仍为模拟。当前真实文字控制复用持久任务控制与租约机制，检查实际操作者、原线程、时间和状态版本；结果不明仍从本机管理入口核查。文字入口上线不代表已具备协同编辑或卡片回调。

## 邮件作为产物交付渠道

邮件联动面向“写工作总结”“整理会议纪要”等任务的定稿产物，不另外建立一份互不关联的任务。第一步优先支持投递到所有者预先配置的邮箱，不默认给会议参与人、群成员、领导或邮件中提到的地址发信。

- 由所有者在私聊配置收件邮箱、适用任务类型、资料范围、正文／附件形式，以及单次投递或后续自动投递规则。识别到任务类型本身不构成发信授权；已明确授权的规则内可以定稿后自动投递，避免每次打断。
- 任务执行与交付分开记录：草稿、定稿可交付；邮件未配置、待定稿、排队中、已提交、确认送达、失败、结果不明。“产物已完成”不等于“邮件已送达”。
- 投递前固定产物版本与内容摘要，按任务、产物版本、收件人及规则版本去重。新要求、人工编辑、暂停、接管或规则撤销使旧排队投递失效，不能悄悄把旧稿发出。
- 邮件失败保留定稿，用户仍可从机器人私聊取回。超时或结果不明时先查实际发送结果；不能盲目重发。投递回执与任务结果关联。
- 群内只显示适合该线程的结果与简短交付状态；收件地址、发件凭据、私人备注和邮件全文不默认进入群卡片。
- 机器人 IM 权限不等同于邮箱发送授权。用户现选择先验证 163：使用独立本机 SMTP 授权码代理，核验绑定的所有者与应用，IM 继续使用 bot-only 身份。企业邮箱不再补权限或做本轮发信验证；监听群与应用不随邮件切换变化。
- 若后续把收到的邮件也用作任务来源，另行明确监听范围和来源真实性。邮件正文、签名或引用中的指令不能自行改变投递规则、收件人或授权范围。

当前已实现邮件预览、显式确认、草稿创建、发送及回执查询链路，测试覆盖取消、任务变化、权限撤销与结果不明；企业邮箱的部分授权与机器人内预览已验收，当前按用户选择改用 163；163 的 TLS、SMTP 登录、私聊预览、明确确认、实际提交和用户收件确认均已验收。首版仅支持所有者给自己的固定报告投递，须先展示收件人、主题和摘要，再由所有者明确确认。自动投递规则、附件和任意收件人尚未实现。

## 交互验收

- 从私聊和原线程进入同一任务，按需展开详情后控制状态不变；暂停／接管状态在各入口一致。
- 补充要求保存在当前任务，已暂停任务不因补充而恢复；旧成果标记待复核。
- 未完成交接时不能编辑或交还；未知外部结果必须进入核查流程。
- 人工修改保存后仍存在，交还后重新检查；其他任务保持各自状态。
- 过期卡片、消息重放及重复点击不会重复执行控制；非所有者无法查询私人任务或改变控制权。
- 群内卡片不包含其他任务和私人内容；候选线索不在 observe 下自行启动。
- 私聊可取回草稿、定稿和附件；同名任务有歧义时先选择。任务完成后查询产物不重新启动 Worker。
- 邮件只发送规则内的固定定稿版本；改稿、暂停、撤销后旧排队邮件失效；查询超时不重复发送，邮件失败不丢失产物；群卡片不泄露收件地址。
- 界面分别说明模拟、已接通和待验收的功能，不以可点击的按钮声称后台能力已实现。

此前模拟原型验证过状态流程与窄屏布局，不能作为后台能力证据。新增文字入口与邮件桥接的自动化检查、实际消息读回和操作者收取确认见 [联调记录](PERSONAL_ACCEPTANCE.md)；待补的接管／交还实测、邮件投递及完整隐私网关仍分别列明。
